# Zaps

A small workflow automation app inspired by Zapier's Zaps: a trigger plus an action. In this version one Zap works end to end: **when a pull request is opened on a GitHub repo, comment on that pull request.** Other apps (GitLab, Jira, Linear, Slack) appear in the app picker as "coming soon".

MEAN stack: MongoDB, Express 5, Angular 16 (+ Angular Material), Node 18, TypeScript. It runs **locally only**.

**What you can do:** sign in with GitHub; list, create, edit, turn on/off and delete Zaps; pick a public repo you admin as the trigger; write the comment with fields from the pull request (`{{pr.title}}`, `{{pr.author}}`, …) and a live preview. There's no run history screen; runs are readable through `GET /api/zaps/:id/runs` (see [Troubleshooting](#troubleshooting)).

## Prerequisites

- **Node 18.20** via [nvm](https://github.com/nvm-sh/nvm). The repo pins `18.20.8` in `.nvmrc`; Angular 16 doesn't officially support newer Node versions.
- **Docker** (Docker Desktop or similar) for the local MongoDB.
- A **GitHub account** and a **public repository where you're an admin**, to test with. Private repos aren't supported.

## Setup

### 1. Install

```sh
nvm install        # reads .nvmrc
nvm use
npm install        # installs all workspaces: shared, server, client
```

### 2. Start MongoDB

MongoDB runs with a password, generated by you on first setup. Create the root `.env` that `docker compose` reads, with a random password, then start it:

```sh
echo "MONGO_ROOT_PASSWORD=$(node -e "console.log(require('crypto').randomBytes(24).toString('hex'))")" > .env
docker compose up -d
```

This runs `mongo:7` on `127.0.0.1:27017` (unreachable from the rest of your network) with a named volume, so data survives restarts. When the volume is first created, MongoDB sets up the root user `zaps` with that password; you'll use it in `MONGODB_URI` in step 5. Stop MongoDB with `docker compose down`; the data is kept.

The password is only applied to a **new** volume. To change it, or if the volume was created before it was set, recreate the volume (this deletes your local Zaps, users and runs, so seed again in step 6): `docker compose down -v && docker compose up -d`. `.env` is git-ignored; see `.env.example`.

### 3. Create a smee channel

GitHub can't reach `localhost`, so webhooks go through [smee.io](https://smee.io), which forwards them to your machine.

1. Open <https://smee.io/new>.
2. Copy the channel URL, e.g. `https://smee.io/AbC123xyz`. You'll put it in `.env` as `WEBHOOK_PUBLIC_URL`.

### 4. Register a GitHub OAuth App

1. On GitHub: **Settings → Developer settings → OAuth Apps → New OAuth App**.
2. Fill in:
   - **Application name:** anything, e.g. `Zaps (local)`
   - **Homepage URL:** `http://localhost:4200`
   - **Authorization callback URL:** `http://localhost:3000/auth/github/callback`
3. Click **Register application**, then **Generate a new client secret**. Copy the **Client ID** and the **client secret** (it's shown only once).

You don't configure scopes in the OAuth App. The app asks for `public_repo` and `admin:repo_hook` when you sign in.

### 5. Configure `server/.env`

```sh
cp server/.env.example server/.env
```

Fill in the values (each one is explained in `server/.env.example` and in [API.md → Configuration](docs/API.md#configuration-env-vars)):

| Variable | Value |
|---|---|
| `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | From step 4 |
| `WEBHOOK_PUBLIC_URL` | Your smee channel URL from step 3 |
| `SESSION_SECRET` | `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` (at least 32 characters) |
| `TOKEN_ENCRYPTION_KEY` | `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"` (must decode to exactly 32 bytes) |
| `MONGODB_URI` | Replace `<MONGO_ROOT_PASSWORD>` with the password in the root `.env` from step 2 |
| `PORT`, `CLIENT_URL`, `GITHUB_CALLBACK_URL` | The defaults work as-is |

`server/.env` is git-ignored; never commit it. The server refuses to start if any variable is missing or invalid.

> If you ever change `TOKEN_ENCRYPTION_KEY`, the stored GitHub tokens and webhook secrets can't be decrypted anymore. Sign in again, and turn your Zaps off and on again.

### 6. Seed the app catalog

```sh
npm run seed -w server
```

This upserts the app picker's catalog (GitHub, plus GitLab, Jira, Linear and Slack as "coming soon") into MongoDB. Run it once after cloning, and again whenever the seed list in `/shared` changes.

## Running

From the repo root (after `nvm use`):

```sh
npm run dev
```

This builds `/shared` once, then starts four processes in one terminal, with output prefixed by name. Ctrl+C (or any process exiting) stops them all.

| Prefix | What it does |
|---|---|
| `shared` | Rebuilds `/shared` on every change |
| `server` | API on <http://localhost:3000>, restarts on change |
| `client` | Angular app on <http://localhost:4200> |
| `smee` | Forwards GitHub webhooks to `http://localhost:3000/webhooks/github` |

You can also run them separately, one terminal each: `npm run dev:shared`, `npm run dev:server`, `npm run dev:client` and `npm run smee`. `dev:server` and `dev:client` build `/shared` once before starting, so they also work without `dev:shared`; you just won't get live updates when you edit `/shared`.

### Try your first Zap

1. Open <http://localhost:4200> and **Sign in with GitHub**.
2. Click **Create Zap** and pick **GitHub**.
3. In **Trigger**, pick your public test repo. Only public repos where you're an admin are listed.
4. In **Action**, keep or edit the comment. Use **Insert field** to add values from the pull request, such as `{{pr.author}}` or `{{pr.title}}`.
5. Click **Save**, then turn the Zap **on**. This creates a webhook on the repo.
6. Open a pull request on that repo. The comment appears on it within a few seconds.

You can edit a Zap while it's on; the builder then shows "This Zap is on. Saving changes to the repository moves its webhook." If you change its repo, Save creates a webhook on the new repo first, then removes the old one. A change in letter case only (`Acme/API` vs `acme/api`) isn't a move. If the new repo still has an old webhook from this Zap, Save shows a dialog linking to it: delete it on GitHub and save again (see [Troubleshooting](#this-repo-still-has-an-old-webhook-from-this-zap)).

### How a Zap works

1. **Turning a Zap on** creates a webhook on its repo for `pull_request` events, pointing at `WEBHOOK_PUBLIC_URL?zap=<zapId>` with a fresh random secret. The hook's id and the encrypted secret are stored on the Zap. Turning it off (or deleting it) removes the webhook, best-effort.
2. **When a PR is opened**, GitHub posts to the smee channel and `npm run smee` forwards the delivery to `POST /webhooks/github`.
3. **The receiver** finds the Zap by the `X-GitHub-Hook-ID` header and verifies `X-Hub-Signature-256` against the raw body with that Zap's secret. Unknown hooks, disabled Zaps, `ping` and any action other than `opened` are acknowledged with `204` and not recorded; a bad signature gets `401`.
4. It records a **run** as `pending` (keyed by `X-GitHub-Delivery`, so a delivery is processed once), renders the comment template with the PR's fields (cut to 65,536 characters if needed; `@mentions` written in the PR title or description are neutralized, so a PR can't ping people from your account), and posts the comment with the Zap owner's GitHub token.
5. The run becomes `success` (with the comment URL) or `failed` (with the error). The receiver answers `200` either way; a failed comment is never a `5xx`. Runs are kept for 7 days.

## Tests

```sh
npm test                 # shared, then server, then client
npm test -w shared       # shared only
npm test -w server       # server only
npm test -w client       # client only (Karma, watch mode)

# one file
cd server && node --import tsx --test src/path/to/file.test.ts
cd client && npx ng test --watch=false --include src/app/path/x.spec.ts
```

- **Server tests** use an in-memory MongoDB ([mongodb-memory-server](https://github.com/typegoose/mongodb-memory-server)), so Docker isn't needed for tests. The first run downloads a MongoDB 7.0.24 binary (~100 MB) and caches it.
- **GitHub calls** are faked in tests, so no GitHub credentials are needed.
- **Client tests** run in Chrome; root `npm test` uses headless Chrome, so Chrome must be installed.

## Limitations

- **Public repos only**, and you must be an **admin** of the repo to add its webhook.
- **Organization repos** may be blocked if the organization restricts OAuth App access. An org owner has to approve the app (organization **Settings → Third-party Access → OAuth app policy**).
- **Local only:** the app isn't meant to be deployed.
- **Body size limit of 100 KB:** a Zap whose comment template is very long and mostly non-ASCII (emoji, CJK) can't be saved. A pull request with a huge non-ASCII description won't trigger the Zap.
- **No run history screen.** Runs are stored for 7 days and can be read from the API (see Troubleshooting).
- **smee and non-ASCII bodies:** smee re-serializes the webhook body, so the signature check can fail for some PR titles with emoji or accents (see Troubleshooting).
- **Long comments are cut** to 65,536 characters (GitHub's limit), ending in `…`.
- **A revoked GitHub token isn't noticed right away.** Comments fail silently (recorded as `failed` runs) until you next use the app, which then signs you out.

## Troubleshooting

### A comment didn't appear: check the runs

While signed in, open `http://localhost:3000/api/zaps/<zapId>/runs` in the browser (the Zap's id is in the builder URL, `/zaps/<zapId>`). It lists the latest 50 runs with their `status` (`pending`, `success`, `failed`) and `error`.

Also check the delivery on GitHub: repo **Settings → Webhooks →** your hook **→ Recent Deliveries**.

### Retry a failed comment ("Redeliver")

If a run **failed** (for example GitHub had a temporary error), you can retry it:

1. On GitHub, open the repo's **Settings → Webhooks**.
2. Click the webhook whose URL is your smee channel with `?zap=<zapId>`.
3. Open **Recent Deliveries**, select the failed `pull_request` delivery, and click **Redeliver**.

Make sure `npm run smee` and the server are running. Redeliver only helps for **failed** runs. Redelivering a run that **succeeded** or is still **pending** does nothing, so the comment is never posted twice. A run stuck in `pending` (the server stopped mid-request) is never retried, since its comment may already exist. There's one rare exception: if GitHub timed out or errored *after* creating the comment, the run was recorded as failed, and a redelivery posts a second comment.

If the failure was a revoked token, sign in again first, then Redeliver.

### "This repo still has an old webhook from this Zap"

When a Zap is turned off, deleted or moved to another repo, removing its webhook on GitHub is best-effort. If that failed, the old webhook stays on the repo and blocks turning the same Zap on again for that repo (or moving it back there). Nothing was changed: on a toggle the Zap stays off; on a Save the Zap stays on with its old repo and your edits are kept in the form.

1. Click **Open webhook on GitHub** in the dialog, or go to the repo's **Settings → Webhooks** and find the hook whose URL ends in `?zap=<zapId>`.
2. Click **Delete**.
3. Turn the Zap on again, or save again if you were changing its repo.

Leftover webhooks of deleted Zaps don't trigger anything. You can delete them the same way to keep the repo tidy.

### Signature errors (`401`) in dev with non-ASCII PR titles

smee re-encodes the webhook body instead of forwarding GitHub's exact bytes, so the signature check can fail for some payloads, such as PR titles with emoji or accented characters. If you hit this, use a different tunnel that forwards the body unchanged. The signature check is never disabled.

### "Sign-in failed. Please try again."

The GitHub sign-in didn't complete: you clicked **Cancel** on GitHub's authorize page, the OAuth `state` check failed (for example, the sign-in was started in another browser or its session expired), or GitHub returned an error such as a callback URL mismatch. Check that `GITHUB_CALLBACK_URL` in `server/.env` matches the OAuth App's **Authorization callback URL**, then sign in again.

### "Your GitHub session expired, please sign in again"

The app's GitHub token was revoked or expired, for example after you revoked the app under GitHub **Settings → Applications**. The first action that calls GitHub (loading your repos, turning a Zap on, moving it to another repo) signs you out and shows this message on the login page. Sign in again. Turning a Zap off or deleting it still works with a revoked token. While the token is invalid, your Zaps can't post comments; those runs are recorded as `failed` (retry them with Redeliver after signing in).

### Nothing arrives after changing the smee channel

Each webhook stores the full `WEBHOOK_PUBLIC_URL` it was created with. If you change it in `server/.env`, restart the server and `npm run smee`, then turn each Zap off and on again so its webhook points at the new channel.

## Project layout

```
client/   Angular 16 app (standalone components, Angular Material)
server/   Express 5 API + GitHub webhook receiver
shared/   Types, zod schemas and the template renderer, used by client and server
```

npm workspaces; one `package-lock.json` at the root. `/shared` compiles to `shared/dist`, which client and server import. `client/README.md` is the Angular CLI's generated readme.
